# Synchronization and conflict policy

What the backend does today when a phone uploads field records: daily
records, weight samples, sales, inventory usage and routine ticks. Each row
is one rule, the code that implements it, and the test that proves it. The
rules describe the code as it is. The manuscript review's tests found eight
places where the code broke its own rules; all eight are fixed, and they
are listed with their fixes under
[Found by the review and fixed](#found-by-the-review-and-fixed).

Paths are relative to the repository root. `test_x.py::Class::test` is a
pytest node id.

## What the frontend does with each response

Read from `HostileEarl/checkngo-frontend` at 563d740 (`src/hooks/useSync.ts`,
`src/lib/db.ts`, `src/lib/api.ts`, `src/components/NeedsAttention.tsx`),
not changed. Daily records, sales, usage logs and routine ticks are saved to
an on-device outbox first and leave only through the four bulk-sync
endpoints, in chunks of at most 60, with the device's UUID and
`recorded_at`. Editing an existing sale and correcting a record are online
calls, not queued.

| Response | The backend sends it when | The frontend |
|---|---|---|
| 200, `failed[]` empty | Every record was created or updated | `markSynced(created + updated)`: the entries leave the outbox |
| 207 | Some records failed (lock, closed batch, house scope, date conflict, an id already in use, a date that cannot change) | Created and updated entries leave the outbox. Each `failed[]` entry, matched by `record_date` for daily records and by `id` otherwise, is `markRejected`: blocked and never re-sent automatically. `classifyError` turns the message into what the worker sees: *locked*, *batch closed*, *more birds than the batch has*, *this day is already recorded* (offers **Replace**: fetches the server's record for that date and re-queues the worker's numbers under the server's id, so the next sync overwrites it, i.e. rule 2), *not assigned to this house*, *sacks do not add up*, or *the server would not take this* (which is how "This id is already in use." and "a re-sync cannot move it to another day" are shown). The worker can edit (re-queue), retry, or discard it |
| 400 with per-record errors (`records[i]`) | A record failed validation, so nothing in the request was written | Only the named records are blocked; the others stay queued and go out on the next pass without them |
| 400 for the whole request | More than 60 records, or two entries for one date | Handled like a network failure (row below). The app never sends this: it chunks at 60 and keeps one queued entry per batch and day |
| 403 | No active membership on the farm, an unrotated PIN, or a single request outside the worker's houses | `markAttemptFailed` for the whole chunk. Blocked at once if the message classifies ("not assigned to" → *not assigned*); otherwise counted as a transient failure and retried, then blocked as *Could not reach the server. Tried 5 times* after `MAX_TRANSIENT_ATTEMPTS = 5`. So a worker whose membership was revoked sees five retries and then a connectivity message |
| 401 | The access token expired | `lib/api.ts` refreshes once (one shared refresh for all waiting requests) and replays the request. A refused refresh clears the session and the user must log in again |
| 5xx, timeout, offline | Server error or no network | `markAttemptFailed`: *retrying*, up to 5 attempts, then blocked as *gave up* |

### What a client receives differently

| Request | Before | Now | The current frontend |
|---|---|---|---|
| Bulk sync record whose id belongs to another farm, batch or house | usage and ticks: `updated` (and the other farm's row changed); daily records and sales: `failed[]` with a raw database error | `failed[]`, "This id is already in use." | Blocks it as *the server would not take this*, showing the message.
